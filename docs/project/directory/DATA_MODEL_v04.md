# Native Places — модель данных v0.4 (проектирование, НЕ миграция)

**Статус:** целевая схема для будущих патчей. Действующая v0.3 таблица `directory_entries` и таблица аудита `directory_entry_events` остаются без изменений до отдельной согласованной миграции.

## Новые сущности и связи

| Сущность (рабочее имя) | Назначение | Основные связи |
|---|---|---|
| `directory_segments` | именованные участки конкретной реки, отдельная геометрия, порядковый номер, краткое описание | `river_entry_id → directory_entries.id` |
| `directory_species` | единая база видов: рыбы, птицы, млекопитающие, растения и т. д.; `common_name`, `scientific_name`, `kind` | не дублируется на каждой реке |
| `directory_species_occurrences` | доказанная связь «вид в водоёме / участке / ООПТ» с источником и датой проверки | `species_id`, `entry_id`, `segment_id?`, `source_id` |
| `directory_media` | фото, превью, автор, лицензия, источник, атрибуция, `alt`, варианты размеров | к объекту/участку/виду через таблицу связей |
| `directory_sources` | источник факта, тип источника, дата сверки, использование данных | связывается с конкретным фактом/геометрией |
| `directory_protection` | официальный статус ООПТ, категория, ссылки на акты/реестр, ограничения и дата актуализации | `entry_id → directory_entries.id` |
| `directory_related_places` | добровольные связи справочных объектов с существующими платными объявлениями | `entry_id ↔ places.id`, без изменения оплат |

Состав полей, ограничения FK, уникальность и индексы уточнить по **фактической** БД и PHP-файлам на хосте. Не запускать SQL по этой схеме как готовую миграцию.

## Модель подтверждения информации

- `source_url` у объекта v0.3 не покрывает разные факты: рыба, сезонность, границы и режим доступа требуют **своих** источников.
- Присутствие вида в реке **не означает** присутствия на конкретном участке. Связь с участком создаётся отдельно с подтверждением.
- Источник OSM подходит для **геометрии**, но не заменяет проверку ихтиофауны или действующего режима ООПТ.
- Для фото обязательно иметь условия использования, автора/источник и дату/основание разрешения. Внешние hotlink-URL не использовать без необходимости и прав.
- Для редких/охраняемых видов скрывать точную геолокацию, если публикация может причинить вред.
- Для границ угодий и ООПТ использовать проверяемую геометрию и дату актуальности; статус области сам по себе не подтверждает разрешение посетителю на деятельность.

## Совместимость с текущим кодом

- Сейчас `directoryConfig.js` знает `river`, `lake`, `forest`, `natural_area`, `hunting_ground`, `landmark`, `spring`. Новый тип `protected_area` — **предложение**, его ещё нет в проверенном коде v0.3.
- Чтобы добавить `protected_area`, нужно синхронно обновить валидацию PHP API, админские значения типов, публичный реестр, SEO-маршрутизацию, карту и тесты.
- Можно добавить `protected_area` через отдельный `type` и поле `legal_subtype`: `zapovednik`, `zakaznik`, `national_park`, `natural_park`, `nature_monument` и т. д.; окончательно сверить с официальной терминологией и статусами объектов.
- Участок не обязан быть самостоятельным `directory_entry`: он может быть дочерней записью реки с новым публичным маршрутом. Избегаем множества отдельных копий одной реки.
- Виды рыб — единый каталог, даже если UI редактирования встроен в вкладку «Реки и водоёмы». Текущий `/admin/dictionaries` не считать базой проверенных находок.

## Поток публикации (проект)

`черновик → проверка геометрии/источников/прав → публикация → публичный API + SEO + карта`; при снятии с публикации API скрывает запись. Новые типы не должны открывать обход платной публикации объявлений.

## Обязательная проверка перед миграциями

Получить текущую схему, актуальные серверные `api/admin/directory/*`, `api/directory/*`, правила CSRF/сессий и `seo/directory.php`. Работать отдельными ZIP для локальных исходников/документации и серверного PHP/SQL; резервное копирование и откат обязательны.
