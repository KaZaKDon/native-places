# Native Places — миграция auth-БД, шаг 3

Дата подготовки: 9 августа 2026 года.  
Целевая СУБД: MariaDB 10.5.x.

Это совместимая миграция четырёх подтверждённых таблиц:

```text
users
user_consents
email_verification_tokens
password_resets
```

Текущий PHP после миграции продолжит работать. Поле `users.is_email_verified` пока не удаляется, потому что установленный PHP временно обращается к нему. Его удаление будет отдельным вторым проходом вместе с обновлением кода.

## Содержимое

```text
sql/00_PRECHECK.sql   только проверяет, ничего не меняет
sql/01_MIGRATION.sql изменяет auth-схему
sql/02_VERIFY.sql     проверяет результат, ничего не меняет
sql/03_ROLLBACK.sql   возвращает исходную схему при необходимости
```

Документ для репозитория:

```text
docs/project/database/2026-08-09-auth-schema-migration.md
```

## Что меняет миграция

- приводит три `user_id` к типу `BIGINT UNSIGNED`, совпадающему с `users.id`;
- добавляет три внешних ключа с `ON DELETE CASCADE`;
- меняет SHA-256-хеши токенов на `CHAR(64) ASCII BINARY`;
- расширяет `user_consents` до журнала событий принятия и отзыва;
- удаляет старое ограничение, запрещавшее повторное событие той же редакции;
- добавляет индексы журнала согласий и токенов;
- синхронизирует `is_email_verified` с `email_verified_at`;
- не удаляет существующие данные.

## Важное ограничение MariaDB

`ALTER TABLE` выполняет неявный `COMMIT`. Поэтому обычный `START TRANSACTION` не может сделать несколько `ALTER TABLE` одной откатываемой транзакцией. Защитой служат:

1. сохранённая резервная копия;
2. обязательный `00_PRECHECK.sql`;
3. выполнение миграции в период без регистраций и восстановления паролей;
4. `02_VERIFY.sql` сразу после миграции;
5. отдельный `03_ROLLBACK.sql`.

## Порядок выполнения

### 1. Короткое техническое окно

На время выполнения не регистрировать пользователей и не запускать восстановление пароля. При небольших таблицах операция должна занять считанные секунды.

### 2. Выполнить `00_PRECHECK.sql`

В phpMyAdmin выбрать базу `vnuko1796_nativeplaces_dev`, открыть вкладку SQL и выполнить файл.

Перед продолжением должны выполняться условия:

- `orphan_user_consents = 0`;
- `orphan_email_tokens = 0`;
- `orphan_password_resets = 0`;
- оба `invalid_*_hashes = 0`;
- оба `duplicate_*_hashes = 0`;
- запрос будущих FK не возвращает строк.

`inconsistent_email_verification_rows` может быть больше нуля: миграция это исправляет.

Последний большой результат со всеми `user_id`, `owner_id`, `sender_id` и `moderator_id` сохранить скриншотом. Он понадобится для следующей общей миграции пользовательских связей всего проекта.

### 3. Выполнить `01_MIGRATION.sql`

Запустить файл один раз целиком.

Если phpMyAdmin покажет красную ошибку:

- остановиться;
- не запускать файл повторно;
- не отключать `FOREIGN_KEY_CHECKS`;
- прислать полный текст ошибки и название последней успешно выполненной команды.

### 4. Выполнить `02_VERIFY.sql`

Ожидается:

- три строки внешних ключей;
- три новых индекса;
- все значения в общей проверке равны `0`;
- события согласий имеют `event_type = accepted`;
- ранее созданные записи сохранились.

### 5. Проверить сайт

После SQL выполнить:

1. вход существующего пользователя;
2. обновление страницы после входа;
3. регистрацию нового тестового email;
4. подтверждение email;
5. восстановление пароля;
6. просмотр согласий в БД.

У новой регистрации в `user_consents` должны заполниться:

```text
event_type = accepted
event_at = время регистрации
source = registration
```

`document_hash` пока будет `NULL`. Он начнёт заполняться после подключения реестра юридических документов.

## Когда применять rollback

`03_ROLLBACK.sql` нужен только при подтверждённой несовместимости после успешного завершения миграции.

Не применять rollback, если после миграции уже начали записываться:

- события `withdrawn`;
- повторные принятия одной версии документа.

В этом случае старый уникальный индекс восстановить уже нельзя без потери событий; используется восстановление из резервной копии или отдельная корректирующая миграция.

## Что намеренно не входит в этот шаг

- удаление `users.is_email_verified`;
- изменение остальных таблиц с `user_id`, `owner_id`, `sender_id`, `moderator_id`;
- единый формат времени UTC/ISO 8601 во всём API;
- endpoint отзыва рекламного согласия;
- заполнение `document_hash`;
- таблица серверных web/mobile-сессий.

Для этих изменений сначала нужен результат инвентаризации пользовательских колонок из `00_PRECHECK.sql`.
